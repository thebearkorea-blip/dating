## §1 설계 원칙 (구조에 직접 영향을 주는 제약)

1. **앱이 말하지 않는다.** 사용자에게 보이는 글은 원칙적으로 캐릭터를 거친다. 앱 목소리가 허용되는 화면은 흰 목록(가입·연령 확인·AI 고지·설정·안전 알림·다음날 아침 유료 안내)으로 코드에 고정하고, 그 밖의 모든 상황(한도 도달·오류·휴식)은 캐릭터의 사정으로 표현한다.
2. **세 층은 쓰기 권한이 다르다.** 공개 층(1개)·집단 층(1개)·개인 층(사용자 수만큼). 공개 층은 성장 대본과 집단 층 결과만이 쓸 수 있고, 결제는 개인 층의 "권한" 한 곳에만 쓴다. 이 분리를 문서가 아니라 DB 권한과 테스트로 강제한다(§2.4).
3. **1단계는 "채팅 없는 엔진"이다.** 앱이 없어도 캐릭터 바이블·일정·일기·사진·검수 규칙은 2단계 엔진의 입력과 같은 형식(파일)으로 만든다. 1단계에서 공개된 모든 사실은 캐논 로그에 쌓여 2단계 사용자의 아카이브가 된다.
4. **넘지 않을 선은 설정값이 아니라 가드다.** `policy` 모듈은 LLM 앞(입력 검사)과 뒤(출력 검사)에 서며, 캐릭터 설정·관계 모드·결제 상태로 꺼지지 않는다.
5. **지어내지 않는다.** 캐릭터가 말하는 과거는 캐논 로그(공개 사실)와 개인 기억(이 사용자와의 사실)에서만 나온다. 생성 결과는 이 두 기록과 대조한다.
6. **세계 시계는 하나다.** 모든 사건은 절대 시각(UTC)으로 기록하고, 사용자는 "언제 들어왔나"(관계 시작 시각)만 다르다. 사용자별로 시간선을 복제하지 않는다.
7. **비용은 LLM 호출 수가 결정한다.** 무료 하루 5회·유료 하루 100회(2026-11-13 결정). 답장 1회 = LLM 호출 1회를 기본으로 하고, 기억 추출·검수·선톡 결정은 배치로 돌린다. 모델 등급(대화용/판단용)을 호출 지점마다 고정한다.
8. **아이돌 설정은 콘텐츠에만 산다.** 엔진(일정·선톡·기억·애정·토라짐)은 "바쁜 일정이 있는 사람"만 알고 아이돌을 모른다. 1단계 실패 시 "한국인 남자친구" 전환은 `content/`만 바꾸는 일이어야 한다.

## §2 전체 구조

### §2.1 단계 1~4를 관통하는 구성도

```
                 ┌──────────────────────────────────────────────────────┐
                 │  content/  (저장소 안의 파일 — 1단계부터 존재)         │
                 │   world/timeline.yaml   성장 대본 (T0=데뷔일 상대일)    │
                 │   world/canon.jsonl     공개된 사실 로그 (append-only) │
                 │   characters/<id>/      bible · voice · schedule       │
                 │                         diary/ · photos/manifest       │
                 │   policy/               lines.md · guards.yaml · safety│
                 └───────────────┬──────────────────────────────────────┘
                                 │ import (2단계: DB 적재 스크립트)
   1단계 (앱 없음)               │                    2단계~ (앱)
┌──────────────────────┐         │   ┌──────────────────────────────────────────┐
│ src/tools (CLI)      │         │   │ apps: Next.js PWA  (Vercel)              │
│  diary 초안 생성      │◄── 공유 ─┼──►│  /chat  /feed  /archive  /me(그가 아는 나) │
│  캡션·사진 태그       │  모듈    │   │  /settings  /admin(운영자)               │
│  검수(reviewer)      │         │   ├──────────────────────────────────────────┤
│  게시 큐·게시 로그    │         │   │ src/engine (순수 함수, DB 모름)           │
└──────────┬───────────┘         │   │  schedule · affection · sulk · persona   │
           │ 사람이 고름          │   │  canon-check · catch-up · app-voice 목록  │
           ▼                     │   ├──────────────────────────────────────────┤
   인스타 · 틱톡 (가상 캐릭터 표시) │   │ src/policy (가드: 입력·출력·연령·사진)     │
                                 │   ├──────────────────────────────────────────┤
                                 │   │ src/jobs (Cron·Queue 소비자)              │
                                 │   │  growth-tick · proactive · memory-extract │
                                 │   │  daily-affection · review-sample          │
                                 │   └───────┬───────────┬───────────┬──────────┘
                                 │           │           │           │
                                 │     Postgres(Neon)  Blob(사진)  AI Gateway(LLM/TTS)
                                 │     schema: world / collective / personal / billing
```

- **1단계**: `content/` + `src/tools` + `src/engine`의 일부(schedule·persona·canon-check) + `src/policy`의 검수 규칙. 사람이 결과를 고르고 SNS에 올린다.
- **2단계**: `apps/web`과 `src/jobs`가 추가되고, `content/`를 DB에 적재한다. 1단계 모듈은 그대로 쓴다. **첫 출시(2026-11-13 결정)는 `/chat`·`/me`·`/settings`와 `proactive`·`memory-extract`·결제만.** `/feed`·`/archive`·`growth-tick`·투표·`collective` 잡은 결제 확인 뒤(스키마는 정의만).
- **3단계**: 공개 층 화면(`/feed`·투표)과 `collective` 스키마, 안전장치(팬 모드)가 켜진다. 엔진 변경 없음 — 관계 모드 값만 `fan`이 추가된다.
- **4단계**: 음악·영상은 `world_events`의 한 종류(데뷔 이벤트)와 `photos`와 같은 미디어 매니페스트로 들어온다. 구조 변경 없음.

### §2.2 1단계 산출물의 형식 — 2단계 엔진이 그대로 읽는다

| 파일 | 내용 | 1단계 용도 | 2단계 용도 |
|---|---|---|---|
| `content/world/group.yaml` | 그룹 id·이름·콘셉·멤버 id 목록(주인공 1 + 조연 3~4)·T0(데뷔 목표일, 미정이면 null) | 일기·게시물의 세계관 근거 | `world.groups`·`world.members` 적재 |
| `content/world/timeline.yaml` | 성장 대본. 각 비트 = `{id, rel_day: T0 기준 상대일(최소·최대), requires:[비트 id], branch: 집단 조건, public_text, kinds}` | 어떤 날 어떤 주제의 일기·사진을 올릴지 | `growth-tick`이 비트를 `world_events`로 발화. 집단 층이 `rel_day` 창 안에서 시점·분기를 정함 |

| `content/characters/<id>/bible.yaml` | 기계가 읽는 설계서: 위 내용을 필드로. `never:[]`·`affection_stages:[{stage, behaviors, reply_delay, initiative}]`·`knows_nothing_about:[]`(그가 모르는 것) | 검수 규칙의 입력 | `persona` 모듈이 시스템 프롬프트를 조립(프롬프트 캐시 대상) |
| `content/characters/<id>/voice.md` | 말투: 사용자 언어를 **완벽하게** 쓴다(언어 자동, 설명 없음)·감정 격해질 때 한국어 튀어나오는 조건·금지 표현·예문 20개(영어 기준, 2026-11-13 결정) | 캡션 톤 | 프롬프트 일부 + 검수의 "말투 일관성" 기준 |
| `content/characters/<id>/schedule.yaml` | 주간 템플릿(요일·시간대·활동·바쁨 0~3) + 예외 규칙(컴백 주간 등은 timeline 비트가 덮어씀) + 랜덤 이벤트 목록(확률·효과) | "오늘 뭐 했나" 일기 근거, 게시 시각 | `schedule` 모듈 입력. 답장 지연·말투·선톡 시점 결정 |
| `content/characters/<id>/diary/YYYY-MM-DD.md` | frontmatter `{date, rel_day, activity, mood, photos:[id], audience: public}` + 본문 | SNS 캡션·일기 원문 | 아카이브 + 선톡 소재("그때 썼던 일기") |
| `content/characters/<id>/photos/manifest.jsonl` | `{id, blob_url, situation, time_of_day, place, face: bool, audience: public|private, used:[{where, at}]}` 파일은 Blob/외부 저장, 저장소에는 목록만 | 게시용 선택 | 선톡·피드에 상황 태그로 검색. `private`는 앱 전용(그가 나에게만 보낸 사진) |
| `content/characters/<id>/scenes/first-meeting-*.md` | 첫 만남 대본(우연한 만남). 관계 시작 시점(연습생기·데뷔 후)별 변형 | 1단계 없음(2단계 전에 작성) | 온보딩 |
| `content/policy/lines.md` | 넘지 않을 선 원문(요약 §"넘지 않을 선") | 검수자 기준 | 변경은 사용자 결정만 |

핵심은 두 가지다. (1) 1단계에서 "사람이 고른 것"만 `canon.jsonl`에 들어가므로 2단계 캐릭터는 1단계에 실제로 공개된 과거만 안다. (2) 사진은 처음부터 `audience`로 나눠 두어야 2단계에서 "SNS에 올렸던 사진을 나한테만 보낸 것처럼" 말하는 모순이 생기지 않는다.

### §2.3 세 층 데이터 모델과 시간선

Postgres 스키마 4개로 층을 물리적으로 나눈다.

```
world (공개 층, 1개)                      collective (집단 층, 1개)
  groups, members                          votes(user_id, event_id, choice)  -- 1인 1표, 가중치 열 없음
  world_events(id, at, kind, title,        vote_tallies(event_id, choice, n)
     body, canon, source: script|branch,   activity_daily(date, active_users,
     rel_day, timeline_beat_id)               messages, feed_views)
  canon_facts(at, character, fact, src)    growth_state(current_rel_day, speed,
  media(id, kind: photo|clip|audio|song,      pending_beats[])
     tags, audience, blob_url)

personal (개인 층, 사용자마다)             billing (권한만)
  users(id, display_name, tz, birth_year   entitlements(user_id, plan, daily_quota,
     _verified, age_band: 14-17|18+)          quota_used_today, quota_exhausted_at,
  relationships(user_id, character_id,        call_credits)
     started_at, mode: fan|romance,        stripe_events(raw)
     stage, affection, sulk_state,
     last_contact_at, push_window, push_max)
  messages(rel_id, at, from: user|char|member,
     text, media_id?, tts_url?, origin: reply|proactive|catchup)
  memories(rel_id, fact, learned_at, source_msg_id, user_visible, deleted_at)
  narrations(rel_id, world_event_id, text, told_at)   -- 같은 사건을 그가 나에게 어떻게 말했나
  disclosures(rel_id, secret_id, told_at)             -- 나한테만 털어놓은 것 (bible의 secrets 풀에서)
  ratings(msg_id, user_id, score, note)               -- 베타 대사 평가
  review_findings(msg_id, rule_id, severity, at)
```

**시간선.**
- 세계 시계는 하나(UTC). 성장 대본은 `rel_day`(T0=데뷔일 기준 상대일)로 쓰고, `growth_state.current_rel_day`가 실제 날짜와 짝을 이룬다. 집단 층이 속도를 바꾸면 `rel_day` 진행이 빨라지거나 느려질 뿐 절대 시각은 그대로다.
- 1단계 운영 시작일이 `rel_day = -180 ~ -365` 어딘가다(데뷔 6개월~1년 전). 1단계가 돌아가는 동안 세계 시계는 이미 흐르고 있으므로, 2단계 출시 시점 사용자는 "연습생 중반에 들어온 사람"이 된다. 이것이 요약의 "사용자마다 관계 시작 시점이 다름"의 첫 사례이며, 구조상 특별 처리가 필요 없다.
- 사용자별 차이는 `relationships.started_at` 하나다. `world_events.at < started_at`은 "그가 들려주는 과거"(개인 층 `narrations`에 `past=true`로 생성, 아카이브 화면에서 공개 층 원문 열람). `at >= started_at`은 실시간 전달 또는 따라잡기.
- **따라잡기(3일 비움)**: 별도 생성이 아니다. 선톡은 사용자 접속과 무관하게 일정대로 보내지므로(푸시 여부와 별개로 `messages`에 쌓임) 들어오면 그대로 보인다. 피드는 공개 층을 `last_seen` 이후로 읽기만 한다. 비용 통제를 위해 접속 없는 날이 늘수록 선톡 빈도를 줄인다(엔진의 `catch-up` 규칙: 1일 비움=정상, 2~3일=절반, 4일 이상=하루 1회 상한). 애정도 하락과 같은 입력(`last_contact_at`)을 쓴다.
- 2기 그룹은 `world.groups` 행 추가 + `content/world/`에 그룹 폴더 하나 추가. 사용자 한 명이 여러 캐릭터와 관계를 가질 수 있도록 `relationships`는 `(user_id, character_id)` 쌍이다.

**두 모드.** 같은 캐릭터·같은 엔진·같은 공개 층. 다른 것은 `relationships.mode`와 `users.age_band`뿐이며, 이 둘은 `policy`가 읽어 (a) 연애 표현 허용 여부, (b) 3시간 휴식 알림, (c) 안전 대본 적용을 결정한다. 개인 층은 모드와 무관하게 사용자 간 완전 격리라서 연애 모드 사용자의 서사가 팬 모드 공개 화면에 새지 않는다.

### §2.5 결제가 성장에 영향을 못 주는 구조적 장치

1. **스키마 분리 + 권한**: `billing` 스키마에 쓰는 DB 역할(`role_billing`)은 `world`·`collective`에 쓰기 권한이 없다. `growth-tick`이 쓰는 역할(`role_growth`)은 `billing`을 읽을 수 없다(GRANT 자체가 없음). 결제 웹훅 핸들러는 `role_billing`으로만 연결한다.
2. **데이터 모델에 통로가 없다**: `votes`에 가중치 열이 없고 `(user_id, event_id)`가 유일 키다. `activity_daily`는 사용자 수·메시지 수만 세며 plan별 집계 열이 없다.
3. **테스트로 고정**: "`entitlements`를 비운 상태와 전원 유료로 채운 상태에서 같은 `collective` 입력으로 `growth-tick`을 돌리면 `world_events` 출력이 바이트 단위로 같다"는 회귀 테스트를 둔다. 이 테스트는 `docs/decisions.md`에 📝 → ✅ 전환 근거가 된다.
4. **사용자에게 보이는 약속**: 설정 화면(앱 목소리 허용 화면)에 "결제는 그의 성장에 영향을 주지 않습니다" 한 줄. 이 문장이 거짓이 되는 코드 변경은 위 테스트를 깨뜨린다.
5. 유료의 효용은 개인 층에만: 하루 한도·통화 크레딧·음성 메시지 빈도. "그가 나에게 더 자주 연락한다"는 개인 층이므로 허용, "그가 더 빨리 데뷔한다"는 불가.
